# VBIOS collection, identification and binary comparison


> This chapter records independently checked public references separately from inherited firmware observations. One XFX R9700 device record has two identical driver-loaded software VBIOS reads and one 2 MiB GPU-mediated raw SPI address-space capture for BDF `0000:03:00.0`. The physical board's retail SKU and PCB revision remain unknown; the capture's extent has not been matched to an identified SPI chip capacity. One official ASUS update package and two extracted ROM payloads remain unassociated with a physical card; the updater was not run. See the [source index](../sources/README.md), [card record](../bios/xfx-r9700-0000-03-00-0/CARD.md) and [research gaps](11_Sources_and_Research_Gaps.md). Supplied originals: [N](../sources/originals/notes.md), [R1](../sources/originals/deep-research-report.md), [R2](../sources/originals/deep-research-report%20%281%29.md).

## Collection scope


The goal inherited from N is a verified stock firmware collection tied to exact boards. Two byte-identical software VBIOS reads and one raw SPI address-space capture are recorded for XFX device `0000:03:00.0`. The software reads came from the AMDGPU debugfs blob and the host log says it was sourced from ACPI VFCT. The separate 2 MiB raw capture contains two identical PCIR chains, but the physical chip capacity and full-chip coverage remain unverified. One official ASUS package and its two vendor-supplied ROM payloads are recorded in the central [vendor package catalog](../inventory/vendor_packages.csv); the payloads remain unassociated with a physical card. Acquire software dumps, independent full SPI reads, official vendor update packages and attributed community comparison images as distinct artifact types. A filename such as `R9700_original.bin` is not provenance.

Use [bios/README.md](../bios/README.md) and the shared [manifest](../bios/_template/manifest.csv)/[global inventory](../inventory/roms.csv) schema. Record the physical card, PCI IDs, PCB revision, version/build, file type, source, acquisition method/date/tool version/log, measured byte length and SHA-256. Keep independent reads, read-group comparisons, parent hashes, signature-status evidence and experiment links. Preserve acquisitions unchanged and retain an independent recovery copy.

## Read-only structure map


R2's conceptual model is a physical SPI image containing one or more graphics option-ROM regions, PCI headers/PCIR structures, revisioned ATOM ROM/master/data tables, possible EFI/GOP components and opaque firmware. The actual layout and any multiple copies must be established from the target bytes.

Map each region's offset, length, header/type, revision, pointers, interpretation, integrity coverage and evidence. Candidate table families include FirmwareInfo, VRAM_Info, GPIO/board data, DisplayObject/connector information, voltage and PowerPlay/SMU-related data. Their presence, format and mutability are not assumed.

The dependency-free [ROM triage reporter](../tools/rom_triage.py) validates signatures, lengths, pointer ranges, supported table revisions, overlaps and image boundaries before dereferencing. It reports unsupported structures with warnings rather than guessing an older generation's offsets. Header recognition or successfully opening a file in a legacy editor is insufficient.

## Comparison workflow


1. Archive immutable acquisitions and metadata; measure sizes/hashes before analysis. Compare like abstraction levels first: software-to-software, full-SPI-to-full-SPI, package-to-package.
2. Prefer the same exact board before/after an official update, then independent cards of the same revision; add cross-vendor comparison after identity is documented.
3. Locate image and table boundaries, version/build/board strings, checksums and candidate authentication metadata. Preserve opaque bytes.
4. Produce changed-range and table-aware diffs; distinguish code, board data, metadata, signatures and unexplained regions.
5. Use the inherited ASUS fan-curve release note as a hypothesis about semantics, not proof that every changed range is a fan table.
6. Compare ASRock/ASUS board data versus shared components to investigate R1's common-PMFW report. Matching displayed versions cannot establish equal bytes.
7. Map candidate fields to observable behavior and separate descriptive values, SMU requests, hard board limits, driver overrides and fused policy.
8. Record all unresolved changes and [authentication boundaries](06_Firmware_Security_and_Protections.md) before proposing a write.

N/R2 suggest hash tools, `cmp`, `xxd`, a hex editor/ImHex or VBinDiff, and a bounded parser. UEFITool is relevant only if the actual structure warrants it. No updater or firmware-writing command was run during this research pass. `R9700flash-dump` is read-only; the retained file was inspected with the bounded reporter described below.

## Read-only image triage workflow

Use only an image already associated with a physical card or a clearly labelled vendor package. Keep the source artifact immutable and work on a copy whose origin, byte length and SHA-256 are recorded. A PCI ROM read, a full-chip SPI image, a vendor updater package and an extracted payload have different coverage; never compare or label them as interchangeable.

The Linux kernel documents a binary PCI `rom` resource that is disabled by default. An access attempt on `0000:03:00.0` returned `EIO`; cleanup disabled the resource and no bytes were retained from that attempt. The driver-loaded `amdgpu_vbios` debugfs blob was captured as a separate software dump. A later read-only `R9700flash-dump` capture retained the configured 2 MiB Navi48 address range through `ROM_INDEX`/`ROM_DATA`; its size does not establish the fitted chip's physical capacity or recovery coverage. Record the PCI BDF, vendor/device/subsystem IDs, kernel and acquisition-tool versions, date, size, hash and exact method with each read. See the [kernel PCI sysfs documentation](https://kernel.org/doc/html/v5.9/filesystems/sysfs-pci.html) (checked 2026-10-18), the [captured files](../bios/xfx-r9700-0000-03-00-0/CARD.md) and [acquisition record](../bios/xfx-r9700-0000-03-00-0/evidence/ACQUISITION.md).

For a supplied file, record artifact type, source, card association, acquisition details and tool version separately, then run the reporter on the immutable input. The current CLI can be run on the extracted ASUS payloads with:

```sh
python tools/rom_triage.py bios/vendor-packages/asus/payloads/7551OG.23.8.0.68.AS04.rom
python tools/rom_triage.py bios/vendor-packages/asus/payloads/7551OG.23.8.0.68.AS07.rom
```

It emits JSON to stdout and reads the input without modifying it. It reports:

1. Input path, byte length and SHA-256.
2. PCI option-ROM `55 AA` candidates and bounded PCIR structures, including wrapped candidates. It reports image offsets, lengths, code types, indicators, the PCIR-image byte sum, and the legacy header checksum when the code type and bounded range allow interpretation. A size mismatch is a warning. EFI and unknown code types do not receive a legacy checksum verdict. The UEFI specification describes PCIR structures, 512-byte image-length units, multiple images and EFI code type `03`; these are structural definitions, not evidence of authenticity or board compatibility. See [UEFI 2.10, PCI bus support](https://uefi.org/specs/UEFI/2.10/14_Protocols_PCI_Bus_Support.html) (checked 2026-10-18).
3. Where ATOM structures are present, signature, ROM/master-table offsets, table IDs, revisions, lengths, pointer bounds and malformed/overlapping structures. The pinned Linux [ATOM firmware header](https://github.com/torvalds/linux/blob/32c52ec87d6245ee2d12ed5dd509e40062939b50/drivers/gpu/drm/amd/include/atomfirmware.h) is a public format reference, not proof that this generic parser supports every R9700 revision.

The [ASUS analysis tool](../tools/asus_rom_analysis.py) extends the generic reporter for this package. It reads the ZIP and updater PE headers as bytes, bounds EFI option-ROM contents, decompresses only the bounded type-1 EFI stream when given EDK II TianoCompress, parses the resulting PE/COFF headers and section ranges, and accepts Ghidra reports only when their input hashes match the bounded image or decompressed PE. It decodes only ATOM structures with matching public revisions and valid lengths, compares exact byte ranges, and accounts for every byte as a supported field/literal, an identified structure or code candidate, known padding/repeated data, or explicitly unresolved. In addition to FirmwareInfo v3.5, it decodes UMC v4.0, DCE v4.5, GPIO LUT v2.1, VRAM usage v2.2 and the bounded path array in display-object v1.5. The 128 trailing bytes in display-object v1.5 remain identified but undecoded. GFX v3.1 and SMC/DPM v6.0 have no exact body definitions in the inspected public Linux snapshots and remain unresolved at the field level. The tool does not execute updater or EFI code. It also optionally aligns the existing XFX software-ROM legacy image against the ASUS image. The retained [ASUS report](../bios/vendor-packages/asus/ASUS_ROM_ANALYSIS.md) and [structured output](../bios/vendor-packages/asus/ASUS_ROM_ANALYSIS.json) are tied to measured input hashes. UEFITool remains a possible supplementary parser for supported images; confirm behavior for its exact version before use. It is not an image-acceptance or flashing tool.

The two ASUS payloads each contain four bounded PCIR images at `0x40000`, `0x4e600`, `0x120000` and `0x12e600`, arranged as duplicated legacy/EFI chains. Each EFI image is x64 and compressed. Its UEFI size envelope declares 57,824 compressed bytes (including a valid zero terminator) and 100,560 uncompressed bytes; the compressed-stream SHA-256 is `d1eeeeb544af7486cbec12e03c4f6c553eb518dac693e93ed85d0dc51d825c11`, followed by 440 `0xff` bytes to the 512-byte image boundary. The literal GOP string `GOP AMD REV: 003.009.001.023.008` lies before the compressed-body offset. EDK II TianoCompress decompressed the bounded stream to the declared length; the result is an AMD64 PE32+ EFI boot-service driver with five in-bounds sections and SHA-256 `77779f1c9dd1536338c6d204f82fab865abd8471183e2470942417d25346432b`. Ghidra statically identified 254 functions and decompiled the entry plus three named helpers. The entry routine contains indirect calls through a global function-pointer table, but stripped names and unresolved pointers do not establish GPU-control semantics. Applying linked Microsoft Authenticode procedure step 14 to the decompressed GOP PE computes SHA-256 `77b66e1ac7a2fb9a6bc3cd695376ec055a7edd7378907b65d312406f3f6078f5`; the extra-data range is empty. OpenSSL verifies the PKCS#7 signer signature, and the signed SPC SHA-256 matches this calculated digest. `-noverify` skips certificate-chain validation; signer trust, timestamps and Windows policy remain unassessed. No code or updater was executed. Each payload reports 38 ATOM records, including two copies each of the master table and 17 pointed data tables. Both 58,880-byte legacy images have valid 8-bit checksums; no legacy checksum verdict is applied to EFI images. The detailed record preserves hashes, offsets, revisions, string offsets, all 89 AS04/AS07 changed ranges, and a partition of every byte. The two chains are identical within each payload, but this does not establish a dual-BIOS topology or recovery path.

AS04 and AS07 contain 3,575 differing bytes across 89 exact ranges. Every discovered ATOM record, including the decoded tables and opaque SMC/DPM v6.0 and GFX v3.1 bodies, is byte-identical between versions. The ASUS version identifier and several timestamp strings change. Additional ranges outside decoded fields remain unresolved and are explicitly classified in the JSON. The ASUS fan-curve note remains a hypothesis: no table schema or changed field has been linked to fan behavior. UMC v4.0 has `vram_type=0x70` (GDDR6) and `umc_config1=0x00010000` (the public `ENABLE_ECC_CAPABLE` bit); this is capability metadata, not proof of ECC correction on an ASUS card. No ASUS CU count or mask is decoded from GFX v3.1. The 64 active CUs recorded for the XFX host are XFX-only evidence. Calculated PE hash streams are recorded for the updater executables and embedded GOP, but these do not establish GPU-side VBIOS signed coverage, flash acceptance, authentication behavior, safety or compatibility with a physical card.

The expanded schema-v5 report maps all 35 master-list slots from the pinned Linux ATOM v2.1 definition, including generic placeholder slots, null pointers, first/second-chain locations, identity hashes and an explanation for each unresolved body. It retains exact before/after bytes for changed ranges up to 256 bytes and hashes plus bounded previews for larger ranges. Table strings, repeated-byte runs and entropy remain candidate leads only. The checked pinned and current upstream Linux snapshots contain no exact SMC/DPM v6.0 or GFX_INFO v3.1 body definition or parser; this does not rule out vendor-private material or every other branch.

The GOP inventory lists all 254 Ghidra-recovered functions, with body ranges, direct and indirect call sites, data references, cross-references, and direct-call entry depth. It records 899 statically resolved direct edges, 186 computed/unresolved call sites, 1,231 function references, three functions in the direct-call-reachable entry graph, and 41 reachable data references mapped to program memory. Computed calls are retained separately even when Ghidra proposes target addresses; stack references remain in the per-function data-reference arrays. The entry code includes indirect function-pointer calls; their targets do not establish GPU tuning semantics. See the complete [Ghidra summary](../bios/vendor-packages/asus/ASUS_ROM_ANALYSIS.json), whose input hash matches the decompressed GOP PE.

The two 58,880-byte legacy images were independently imported into Ghidra 12.1.4 using the 16-bit x86 real-mode language. Each header entry at `0x3` contains `E9 FA 5F`, a relative jump to `0x6000`, which is the analyzed root. For each version, Ghidra recovered 244 functions and 674 direct call sites; the bounded bodies occupy 10,242 bytes across 60 merged candidate ranges. There are 144 functions in the root's direct-call graph. Two indirect call sites at `0000:96d6` and `0000:9e17` have no resolved targets; a separate `INT 0x42` instruction occurs at `0000:9df9`. The remaining image bytes are not assumed to be data or non-executable. Exact functions, body ranges, entry paths, indirect calls, interrupt site, disassembly and entry decompilation are in the [AS04](../bios/vendor-packages/asus/analysis/AS04-legacy-ghidra.json) and [AS07](../bios/vendor-packages/asus/analysis/AS07-legacy-ghidra.json) sidecars, with compact ranges and confidence notes in the main JSON. Static function recovery is not runtime evidence.

Static analysis of both Windows updater executables places the RAR5 marker at `0x6b600`, the first byte after each last declared section. The linked [Microsoft Authenticode PE procedure](https://download.microsoft.com/download/9/c/5/9c5b2167-8017-4bae-9fde-d599bac8184a/Authenticode_PE.docx) step 14 includes extra file data from `SUM_OF_BYTES_HASHED` to the certificate-table size exclusion, covering the RAR5 overlay. For both updater PEs, OpenSSL verifies the PKCS#7 signer signature and the signed SPC image digest matches the independently calculated PE SHA-256. `-noverify` skips signer-certificate chain validation; trust, timestamps and Windows policy remain unknown. Microsoft Learn's PE page has conflicting prose about data past the last section; the calculation follows the linked step-by-step procedure. These updater signatures do not establish archive behavior or GPU-side authentication/acceptance of either ROM payload. See the [Microsoft PE format page](https://learn.microsoft.com/en-us/windows/win32/debug/pe-format), [OpenSSL `smime` documentation](https://docs.openssl.org/3.6/man1/openssl-smime/) and the package-specific [integrity map](../bios/vendor-packages/asus/ASUS_ROM_ANALYSIS.md).

## Bounded XFX cross-card comparison

The existing XFX driver-loaded software VBIOS sample and ASUS legacy option-ROM image each contain one bounded 58,880-byte legacy image. At matching image-relative offsets, 591 bytes differ in 136 ranges. Of 19 ATOM table records aligned by table ID and master-list index, 13 are byte-identical; six have matching lengths and revisions but different bytes: `ATOM_ROM_HEADER` (44 bytes, 8 differences), `firmware_info` (172 bytes, 7), `smc_dpm_info` v6.0 (532 bytes, 6), `display_object_info` v1.5 (200 bytes, 3), `vram_usage_by_firmware` v2.2 (48 bytes, 1), and `unclassified_table_09` v3.3 (852 bytes, 1). The ROM-header pointer is shifted by eight bytes; all other listed structures use the same image-relative offset. Full ranges and values are in the [structured report](../bios/vendor-packages/asus/ASUS_ROM_ANALYSIS.json).

This is evidence about the bytes in one XFX debugfs blob and one unassociated ASUS payload. The XFX kernel log says AMDGPU sourced it from ACPI VFCT, not a physical SPI read; its precise retail SKU and PCB revision are unknown. Shared structures do not establish matching wiring, runtime policy, authentication coverage, image acceptance, or cross-flash compatibility. XFX host CU/ECC observations remain XFX-only and do not establish ASUS capabilities.

## Field-mapping acceptance


A mapping needs a reproducible offset/table revision, plausible type/unit, independent cross-image evidence and an observed behavioral relationship. Permission to edit requires separate integrity/authentication evidence and demonstrated [recovery](05_Flashing_Backup_and_Recovery.md). A mapping alone does not establish that an edited image will boot.
