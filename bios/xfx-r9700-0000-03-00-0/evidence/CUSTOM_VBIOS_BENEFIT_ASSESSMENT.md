# Could a custom VBIOS benefit this XFX R9700?

Assessment date: **2026-10-19**. This is a static research conclusion for the XFX-subsystem device at BDF `0000:03:00.0`. It does not claim that a firmware edit was made, accepted, booted, or measured.

## Scope and evidence standard

The target record is tied to PCI `1002:7551`, subsystem `1eae:9801`, and unique AMD SMI ASIC ID redacted. The retail SKU, PCB revision, card labels, cooler and board circuitry remain unknown. The two 58,880-byte software VBIOS reads match each other and came from AMDGPU's ACPI-VFCT-derived debugfs blob. The 2 MiB `R9700flash-dump` capture is a separate GPU-mediated address-space read: the fitted flash capacity and complete-chip coverage are not verified. None of these files is a qualified recovery image. The ASUS payloads are vendor update files for ASUS `TURBO-AI-PRO-R9700-32G`, not XFX card reads and not established full-chip images.

The [raw/software/ASUS comparison](XFX_ASUS_COMPARISON.md) records the exact hashes, boundaries and offsets. The capture's first legacy chain matches the software-read length but differs in eight bytes. Its known ATOM differences are `firmware_capability` (`0x00024000` versus software `0x00024001`), `mc_baseaddr_high` (`0` versus `0x80`), two display-object support/size fields (both zero versus `0x0688`/`0x1618`), and a reserved VRAM-usage value (`0` versus `8`). The remaining difference is outside a parsed ATOM record. These are not evidence of an XFX tuning restriction. Against ASUS, the raw capture differs by 584/588 legacy bytes (AS04/AS07); the XFX software VBIOS differs by 591/595. The XFX/ASUS SMC/DPM v6.0 tables differ in six bytes and remain opaque. Shared versions, tables or fields do not make ASUS firmware safe for XFX.

Verdict labels mean:

- **Credible VBIOS target:** evidence supports firmware policy as a meaningful control layer for this kind of benefit. It does not establish an editable XFX field or safe image.
- **Possible but unsupported:** firmware could affect the behavior, but this sample provides no mapped, validated XFX edit target.
- **No VBIOS path:** available evidence points to hardware, driver, PSP, OS or platform capability, with no evidence that a VBIOS edit can provide the requested capability.

Confidence describes the evidence for the verdict and mechanism. It is separate from confidence that an edit would work. “Direct” below means a measured local file/host record or checked primary source; “inference” is a conclusion from those facts; “anecdote” is a third-party report.

## Evidence by benefit area

### Fan, acoustics and cooling

**Direct evidence:** ASUS's [official support page](https://www.asus.com/us/motherboards-components/graphics-cards/turbo/turbo-ai-pro-r9700-32g/helpdesk_bios/?model2Name=TURBO-AI-PRO-R9700-32G) says its update refines the fan curve. In the local ASUS payloads, all discovered ATOM records are byte-identical between AS04 and AS07; the changed ranges have not been mapped to a fan field. The XFX and ASUS `smc_dpm_info` v6.0 records differ in six bytes, but that body has no exact public definition in the checked Linux source. The XFX board's fan controller, tach/PWM wiring and thermal baseline are unknown.

**Anecdote:** An [ASUS owner report](https://www.reddit.com/r/LocalLLM/comments/1w8r7rf/psa-for-asus-turbo-ai-pro-r9700-32gb-owners/) attributes a 30%-to-12% minimum-fan change to AS07 and says a full power cycle was needed. The post supplies no payload hash, instrumented noise/temperature data or XFX evidence. A separate comment initially reported no change before the full-power-cycle detail.

**Runtime alternative:** Current Linux [AMDGPU thermal controls](https://docs.kernel.org/gpu/amdgpu/thermal.html) document fan curves, minimum PWM, acoustic targets and power caps. Fan-curve values are staged and committed through the driver interface. These controls are useful only if exposed by the actual XFX driver/PMFW path; none was queried or changed here.

**Verdict:** A fan curve is the best-supported firmware-policy target class because ASUS explicitly describes a vendor fan-curve update. That does not identify an XFX byte to change or justify transferring AS07. For this physical XFX card, support for a custom edit remains unproven.

### Clocks, voltage, power and efficiency

**Direct evidence:** The XFX software image's 172-byte FirmwareInfo v3.5 table has `firmware_capability=0x00024001`, PPLib ID `0x0000125b`, reserved boot-clock and boot-voltage slots, a null `PowerPlayInfo` pointer, and zero mode-specific MACO/USB limits. The raw capture reports capability `0x00024000` and the same PPLib ID. The [public ATOM definition](https://github.com/torvalds/linux/blob/master/drivers/gpu/drm/amd/include/atomfirmware.h) says a nonzero PPLib ID selects a driver-sourced PowerPlay table. Current [SMU14 source](https://github.com/torvalds/linux/blob/master/drivers/gpu/drm/amd/pm/swsmu/smu_v14_0.c) and its [common table parser](https://github.com/torvalds/linux/blob/master/drivers/gpu/drm/amd/pm/swsmu/smu_cmn.c) show one path that consumes this selection. A separate MP1 14.0.2/14.0.3 implementation can obtain a combo table from PMFW; the exact XFX dispatch is unknown. Current [AMDGPU power-management code](https://github.com/torvalds/linux/blob/master/drivers/gpu/drm/amd/pm/amdgpu_pm.c) documents runtime clock/voltage controls. No general board power limit is decoded, and SMC/DPM v6.0 remains opaque.

**Inference:** A VBIOS can participate in boot defaults and policy selection, but the fields present here do not expose a mapped XFX clock/voltage/power edit. The matching driver-supplied table and PMFW route may be more relevant than an ATOM edit. The host record also logs failed overdrive-table uploads on resume; this is a software/runtime diagnostic lead, not proof that firmware settings are wrong.

**Runtime alternative:** AMD's [R9700 ROCm/PyTorch guide, Rev. 2.0](https://www.amd.com/content/dam/amd/en/documents/products/graphics/workstation/radeon-ai-pro-rocm-pytorch-guide.pdf) documents a compute-optimized profile that favors sustained clocks and higher power limits. Current upstream Linux exposes driver power/clock/voltage controls where supported, including `pp_od_clk_voltage` and the `smu_pptable_id` source selector; AMD SMI also documents runtime controls and telemetry. A third-party [R9700 tuning report](https://github.com/daimonionnn/amd-r9700-vllm-and-tuning-toolkit/blob/main/docs/r9700-oc-uv-findings.md) reports that requested overdrive values did not always match effective DPM and that results changed after cooling service. A [Reddit tuning thread](https://www.reddit.com/r/LocalLLaMA/comments/1t6d9la/9700_pro_users_undervolting_nets_crazy_clocks/) claims high clocks with LACT undervolting, but is uncontrolled, has no matching XFX identity and does not describe a VBIOS modification. These community reports are leads, not transferable settings or proof of stability.

### Memory timing, voltage, ECC and training

**Direct evidence:** XFX and ASUS have the same 84-byte UMC v4.0 record: GDDR6 metadata, a 100 MHz reference clock, and an ECC-capable bit. The default ECC-enable field is clear. AMD's [R9700 specification](https://www.amd.com/en/products/graphics/workstations/radeon-ai-pro/ai-9000-series/amd-radeon-ai-pro-r9700.html) labels memory ECC support Linux-only. The XFX legacy image has null `vram_info` and `voltageobject_info` pointers; its UMC record contains no timing table. `smc_dpm_info` v6.0 is opaque. The [host record](../../../inventory/host_checks.md) reports Samsung through software, but no physical DRAM package marks or population have been observed.

**Inference:** Memory frequency/voltage may be affected by SMU/driver policy, while timings and initialization depend on exact DRAM and PCB routing. The ATOM facts do not justify a timing or voltage edit. Memory ECC capability, default enablement, PSP GECC state and observed correction are separate states. The Linux [AMDGPU module documentation](https://docs.kernel.org/gpu/amdgpu/module-parameters.html) describes `forcelongtraining` for resume; current [PSP source](https://github.com/torvalds/linux/blob/master/drivers/gpu/drm/amd/amdgpu/amdgpu_psp.c) reads a runtime database for two-stage DRAM training, while the pinned [PSP RAS path](https://code.googlesource.com/linux/torvalds/linux/+/a406b8b424fa01f244c1aab02ba186258448c36b/drivers/gpu/drm/amd/amdgpu/amdgpu_psp.c) can request GECC state for a later boot. Neither fact establishes the XFX custom kernel's executed path.

**Runtime alternative:** Read clock/voltage telemetry and use only supported MCLK/SMU controls after identifying the exact driver path. For ECC, inspect PSP/AMDGPU RAS state and counters using supported AMD SMI calls. Training investigation should use the exact driver's documented resume controls. No query, write, tuning run, error injection or workload test was performed.

### Compute units, virtualization and display features

**CUs:** AMD's [R9700 specification](https://www.amd.com/en/products/graphics/workstations/radeon-ai-pro/ai-9000-series/amd-radeon-ai-pro-r9700.html) lists 64 CUs / 4096 stream processors; the [host record](../../../inventory/host_checks.md) reports 64 active CUs on the XFX-subsystem functions. XFX/ASUS GFX_INFO v3.1 is byte-identical, but no exact public v3.1 body definition was found. Current Linux [GFX 12 source](https://github.com/torvalds/linux/blob/master/drivers/gpu/drm/amd/amdgpu/gfx_v12_0.c) derives topology from hardware-visible state, and the [AMDGPU module documentation](https://docs.kernel.org/gpu/amdgpu/module-parameters.html) describes `disable_cu` as a disable path. There is no evidence of usable disabled CUs for a ROM to expose.

**Virtualization:** The [host record](../../../inventory/host_checks.md) shows that its four XFX functions expose no SR-IOV capability. The current AMD [ROCm virtualization matrix](https://rocm.docs.amd.com/projects/install-on-linux/en/latest/reference/system-requirements.html#virtualization-support) lists Radeon PRO V710 for KVM SR-IOV and does not list active R9700. SR-IOV requires device capability, AMD's GIM driver and platform/hypervisor support; no VBIOS change is demonstrated to provide these. Device passthrough is a separate platform use case.

**Physical display outputs:** The [XFX product page](https://helpdesk.xfxforce.com/shop/xfx-amd-radeon-ai-pro-r9700-32gb-gddr6-4xdp-amd-rdna-tm-4) names four DisplayPort outputs; AMD publishes up to four partner-configurable outputs in its [R9700 specification](https://www.amd.com/en/products/graphics/workstations/radeon-ai-pro/ai-9000-series/amd-radeon-ai-pro-r9700.html). A ROM may describe board-specific connector paths, but it cannot add absent connectors, PHYs, or routing. The exact physical XFX board has not been photographed or inspected.

**Display mode and pre-OS output:** XFX contains DCE v4.5 and display-object v1.5. The XFX and ASUS display-object records differ by three bytes; the relevant nested display-object bytes are not mapped to an observed behavior. The ASUS GOP was bounded and statically inspected, with indirect service calls unresolved. Linux [Display Core documentation](https://github.com/torvalds/linux/blob/master/Documentation/gpu/amdgpu/display/index.rst) describes hardware programming and resource management in the OS display driver. A specific reproducible pre-OS or mode-selection defect could motivate further field tracing, but no such XFX fault is recorded. Linux also has a runtime [`virtual_display` parameter](https://docs.kernel.org/gpu/amdgpu/module-parameters.html) for headless/virtualized display heads; it does not create physical outputs.

## Community claims and source quality

Targeted searches on 2026-10-19 for modified/custom GPU VBIOS claims scoped to Radeon AI PRO R9700 found the official ASUS AS07 update and user reports about that update, along with runtime LACT/undervolting claims and vendor-ROM variance notes. They did not locate a public custom XFX R9700 ROM image, hash, byte diff or validated modified-image result. This is a bounded search result, not proof that no such report exists.

The ASUS fan report is a user observation tied to its ASUS model, not a controlled result or an XFX compatibility claim. The R9700 undervolting posts and tuning repository describe driver/software behavior on other cards; they do not report custom GPU VBIOS edits. A community [two-card memory/VBIOS comparison](https://github.com/daimonionnn/amd-r9700-vllm-and-tuning-toolkit/blob/main/docs/r9700-mem-vendor-bios-variance.md) reports different card memory vendors/revisions and non-transferable tuning, reinforcing the need to identify this XFX board and its DRAM before drawing settings from another model.

## Overall assessment and remaining gates

The best-supported possible firmware benefit is a quieter fan policy, based on ASUS's own update note and an owner report. It is credible as a vendor policy target on that ASUS board, but its changed byte is unmapped and nothing shows that the XFX board shares the field, cooling, wiring or runtime behavior. Core/power and memory changes remain possible in principle but unsupported by an identified XFX edit field. ECC control, CU topology, virtualization, and physical display capabilities have separate PSP/driver/hardware/platform paths; the available evidence does not support unlocking them with a custom VBIOS. A specific display compatibility fault remains the only additional narrow use case that could justify further ROM field tracing.

The research-only gates still open are: exact XFX SKU/PCB and physical component identity; independent identification and recovery-qualified SPI coverage; stock workload, power, thermal, acoustic and correctness baselines; exact driver/SMU/PMFW and PowerPlay table selection; field-to-behavior evidence; GPU-side integrity/authentication coverage; and a demonstrated accepted-image route. Until those are evidenced, no ASUS image should be used as an XFX donor and no custom XFX image is justified.
